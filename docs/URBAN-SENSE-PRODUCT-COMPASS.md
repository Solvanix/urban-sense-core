# بوصلة المنتج وخطة الإطلاق — Urban‑Sense

**الحالة:** مرجع قرار معتمد للعمل من مستودع GitHub.  
**المصدر التقني الرئيسي:** [`Solvanix/urban-sense-core`](https://github.com/Solvanix/urban-sense-core) على الفرع `main`.

## 1. تعريف الفكرة بعد تصحيحها

> **Urban‑Sense منصة بلاغات بلدية عربية تنظّم انتقال البلاغ الخدمي غير العاجل من الإرسال إلى المراجعة والإسناد والأدلة والتحقق والإغلاق، مع صلاحيات محددة وسجل تدقيق قابل للمراجعة.**

ليست Urban‑Sense متجرًا أو منصة سياحية أو دليل وجهات أو شبكة اجتماعية أو قناة طوارئ. لا تقاس قيمة المنصة بعدد الشاشات أو الوعود التسويقية؛ بل بقدرتها على منع البلاغات غير الواضحة، تقييد القرارات إلى الأدوار الصحيحة، حفظ الدليل ضمن سياقه، وإظهار الحالة الحقيقية لصاحب البلاغ.

| لمن؟ | ما الذي يحصل عليه؟ | ما الذي لا نعد به؟ |
|---|---|---|
| المواطن | إرسال بلاغ غير عاجل، متابعة حالته، وتقييم اختياري بعد إغلاق معتمد. | زمن استجابة محدد أو معالجة مضمونة أو بديل عن قنوات الطوارئ. |
| موظف الخدمة | مراجعة وتصنيف ضمن البلدية والنطاق المكلف به. | وصولًا مفتوحًا لبلاغات بلديات أخرى أو سلطة إغلاق بلا تحقق. |
| الفريق الميداني | مهمة مسندة ومساحة أدلة مرتبطة بالبلاغ. | تعديل الحالة خارج المسار أو الاطلاع على ما لا يدخل ضمن المسؤولية. |
| المشرف ومدير البلدية | تحقق وإغلاق وحوكمة فريق وسجل أحداث. | مؤشرات أداء أو نتائج ميدانية قبل وجود تشغيل حقيقي وبيانات مجمعة مناسبة. |

## 2. ما هو ثابت وما هو مؤجل

| ثابت في النواة | مؤجل عمدًا |
|---|---|
| الأدوار البلدية، الانتقالات المحكومة على الخادم، الأدلة، التحقق، الإغلاق، التقييم الحقيقي، وسجل التدقيق. | متجر، دفع، سياحة، دليل تجاري، مخطط رحلة، أو تطبيق هاتف أصلي. |
| واجهات عربية RTL للمواطن والعمليات والصفحات العامة. | خريطة عامة للبلاغات قبل مراجعة الخصوصية ووجود بيانات كافية. |
| تجربة بلدية محدودة بحدود غير طارئة. | أرقام أثر أو زمن خدمة أو تقييمات افتراضية أو شهادات مصطنعة. |

## 3. الحالة المتحققة في المستودع

يحتوي المستودع على React وTypeScript في الواجهة، وExpress وtRPC وDrizzle في الخادم، مع مخطط بيانات وسجل تدقيق وقواعد دورة بلاغ واختبارات صلاحيات ومسار. فحص النسخة الحالية أعطى **19 اختبارًا ناجحًا**، وفحص TypeScript وبناء الإنتاج ناجحان. كما نجح مسارا GitHub Actions: `Repository Baseline` و`Web quality` للالتزام [`793b27f`](https://github.com/Solvanix/urban-sense-core/commit/793b27f585582435ef389f87b68412f41f921c5f). [1] [2]

| المجال | الحالة | الدليل أو الملاحظة |
|---|---|---|
| دورة البلاغ | مطبقة ومختبرة | إجراءات الخادم تحمي الانتقالات، والمراجعة والإسناد والدليل والتحقق والإغلاق موجودة في `server/routers/reports.ts`. |
| ضبط الهوية والصلاحيات | مطبق في المسار الأساسي | الإجراءات الخاصة تستخدم `protectedProcedure` وتتحقق من نطاق البلدية والدور والملكية. |
| الأدلة والتدقيق | مطبق | ملفات الأدلة مخزنة بمراجع خارج قاعدة البيانات، والأحداث مرتبطة بسجل تدقيق. |
| الصفحات العامة | مطورة ومختبرة | رأس وتذييل موحدان وصفحتا «كيف تعمل؟» و«للبلديات» واختبار تنقل عام. |
| التكامل المستمر | عامل | فحص النوع والاختبارات والبناء وفحص المسافات البيضاء للتغيير المقدّم. |

## 4. الفجوات التي لا يجوز تجاهلها

التقرير التقني القديم كان يحذر من هوية ضيف مشتركة، غياب RBAC، CORS واسع، غياب أدلة، وترحيلات غير مراجعة. عولجت المخاطر الأساسية الخاصة بالهوية والأدوار ودورة البلاغ والأدلة والترحيلات في المستودع الحالي، لذلك لا ينبغي إعادة بناء المشروع على فرضيات التقرير القديم. لكن التقرير يبقى مفيدًا لأنه يثبت أن الجاهزية لا تأتي من الواجهة وحدها. [3]

| الأولوية | الفجوة الحالية أو شرط الإثبات | قرار العمل |
|---|---|---|
| حرجة قبل تجريب عام | تقييم مواطن حقيقي واحد على الأقل لمسار مكتمل. | لا محاكاة ولا بيانات بديلة؛ يُنجز مع مشارك مستقل. |
| حرجة قبل بيانات مواطنين واسعة | سياسة خصوصية واحتفاظ، مالك خدمة، إزالة وصول، استجابة حادث، واختبار استعادة. | توثق وتشغّل مع البلدية المشاركة قبل التوسع. |
| عالية | حدود معدل صريحة للإرسال وتسجيل الدخول وبدء الرفع والبحث. | إضافة طبقة rate limiting واختبارات رفض قبل التوسع. |
| عالية | CORS وCSRF ومحددات حجم الرفع تحتاج تحققًا قابلًا للاختبار في بيئة النشر. | تثبيت قائمة أصول مسموحة واختبارات تكامل لطلبات الاعتماد. |
| متوسطة | إعدادات وصول عربية قابلة للحفظ. | حجم نص وتباين أعلى وتقليل حركة، مع اختبار يدوي ومراعاة الحركة المفضلة. |
| متوسطة | حجم حزمة الواجهة كبير. | تقسيم المسارات الثقيلة ديناميكيًا بعد قياس حقيقي، لا كتحسين شكلي فقط. |
| متوسطة | الإشعارات وخريطة البلاغات العامة. | تؤجل حتى تصميم خصوصية وموافقة تشغيلية وبيانات حقيقية. |

## 5. محاور التطوير

### المحور A — الثقة والحكم

الهدف هو أن يصبح كل قرار حساس قابلاً للتفسير والاختبار. نضيف حدود المعدل، فحوص CORS وCSRF، مراجعة أحجام وأنواع الملفات، ورصدًا آمنًا للأخطاء من دون إفشاء بيانات. لا يبدأ تجريب مفتوح أو جمع موسع للبيانات قبل مرور هذه البوابة.

### المحور B — المواطن والإتاحة

نحسن ما يحدث قبل إرسال البلاغ: شاشة «هل هذا بلاغ مناسب؟»، وصف الحد غير الطارئ، ما يجب توفره من موقع ووصف، وإعدادات وصول عربية خفيفة. تبقى اللغة مباشرة ولا تتحول إلى نموذج طويل أو واجهة متاجر.

### المحور C — العملية البلدية

نطور لوحة العمليات حول القرار التالي لا حول بطاقات عامة: قائمة مراجعة، حالة إسناد، متطلبات دليل، تحقق مشرف، وخط تدقيق مرئي. لا نضيف مؤشرات أداء عامة إلا بعد وجود تشغيل فعلي وبيانات مجمعة قانونية.

### المحور D — التجربة التشغيلية

التجربة هي وحدة نجاح المنتج: بلدية مشاركة واحدة، فئة بلاغ واحدة، مسؤول خدمة، فريق ميداني، مشرف، سياسة احتفاظ، قناة دعم، ومشارك مستقل يقدم تقييمًا حقيقيًا عند الإغلاق. لا يُعلن الإطلاق كنجاح قبل اجتياز هذه الدورة.

### المحور E — الأداء والنشر

يظل GitHub هو مصدر الشيفرة والحقيقة: كل تعديل يمر عبر فحص النوع والاختبارات والبناء وGitHub Actions. ينفذ النشر إلى بيئة تجريبية بعد نجاح CI، أما الإطلاق العام فيتطلب بوابة أمنية وتشغيلية منفصلة وموافقة مالك الخدمة.

## 6. خارطة التنفيذ

| الموجة | النطاق | مخرج قابل للتحقق | بوابة الانتقال |
|---|---|---|---|
| 0. تثبيت المصدر | توثيق المنتج، تنظيف الواجهة العامة، GitHub Actions. | فرع `main` نظيف، اختبارات وبناء وCI ناجحة. | مكتمل في الالتزامات الأخيرة. |
| 1. حراسة التوسع | Rate limiting، CORS/CSRF، فحوص الرفع، سياسة أخطاء آمنة. | اختبارات قبول ورفض لهذه الضوابط. | لا فشل حرج في الاختبارات أو مراجعة الإعداد. |
| 2. تجربة مواطن قابلة للوصول | إرشاد قبل الإرسال، إعدادات وصول، تحسين إدخال الهاتف والصورة. | مراجعة هاتفية، لوحة مفاتيح، وتقليل حركة. | مستخدم تجريبي يستطيع إنشاء بلاغ غير عاجل بوضوح. |
| 3. عملية بلدية منضبطة | قائمة عمل، تدقيق مرئي، دليل/تحقق، حزمة تشغيل بلدية. | دورة كاملة من مواطن إلى مشرف. | بلدية محددة توافق على التنفيذ التجريبي. |
| 4. إثبات التجربة | تجربة حقيقية محدودة، تقييم مواطن حقيقي، مراجعة خصوصية ودعم. | تقرير تجريبي مجمع بلا بيانات تعريفية. | يقرر المالك التوسع أو التعديل. |
| 5. التوسع المدروس | إشعارات، مؤشرات مجمعة، تحسين الأداء، وربما خريطة خاصة. | تصميم خصوصية وقياس حقيقي ومراجعة تكلفة. | لا إضافة قبل تحقق موجة سابقة. |

## 7. مسار التعديل والاختبار والنشر

| المرحلة | الإجراء الإلزامي |
|---|---|
| تعريف تغيير | توثيق المشكلة والقبول في `apps/web/todo.md` أو بطاقة قرار. |
| تنفيذ | شيفرة في `apps/web` مع عدم لمس أسرار أو بيانات تشغيلية حية. |
| اختبار محلي | `pnpm check` ثم `pnpm test` ثم `pnpm build`. |
| مراجعة مصدر | فحص الفرق، واختبار المسافات البيضاء للتغيير فقط. |
| دمج GitHub | التزام وصفي ودفع إلى `main` بعد النجاح، مع مراقبة `Repository Baseline` و`Web quality`. |
| نشر تجريبي | بيئة مخصصة ومراجعة رابطها من دون بيانات حقيقية غير مصرح بها. |
| إطلاق عام | موافقة مالك الخدمة بعد اجتياز بوابة الأمان والتشغيل والتجربة الحقيقية. |

## 8. قرار النشر

«النشر» ليس معنى واحدًا. **النشر البرمجي** يتم إلى GitHub عند دفع التزام ناجح وفحوص CI ناجحة. أما **نشر الخدمة للمواطنين** فيحتاج بيئة تشغيل، نطاقًا، إعداد أسرار، مالك خدمة، وسياسة بيانات وتجربة محدودة مع بلدية فعلية. لذلك لن تساوي الخطة بين نجاح البناء وبين الجاهزية لتلقي بلاغات مواطنين على نطاق واسع.
