# SENSE Tourism Canvas — العيزرية

**الإصدار:** 1.0 — سبتمبر 2026  
**الحالة:** Canvas استراتيجي قابل للمراجعة، وليس إثباتًا للسوق أو شراكة أو اعتمادًا رسميًا.  
**النطاق:** منصة قصص وتجارب سياحية مسؤولة تبدأ من العيزرية، وتربط المحتوى العام ببطاقات مسارات قابلة للتحقق وملفات جاهزية لأصحاب التجارب.

> **الفكرة المركزية:** العيزرية ليست محطة عبور. SENSE تساعد الزائر على رؤية طبقات المكان، وتساعد صاحب التجربة على إظهار حدود الجاهزية، وتساعد الجهات المعنية على مراجعة ما يمكن نشره قبل تحويله إلى وعد أو حجز.

## 1. المشكلة

المعلومات السياحية في العيزرية متفرقة بين قصص شفوية، معالم دينية، صفحات عامة، خرائط، وسائل تواصل، مزودين محليين، وذاكرة السكان. لا يوجد حتى الآن مسار موحد يوضح للزائر الفرق بين القصة، والمصدر، والوصول الفعلي، وما يمكن حجزه، وما يزال مجرد فكرة أو فرضية.

ينتج عن ذلك ثلاث مشكلات مترابطة:

1. **للزائر:** يصعب معرفة ماذا يرى، وكم تستغرق التجربة، وهل الوصول متاح، ومن المسؤول، وما الذي ينبغي احترامه.
2. **لصاحب التجربة:** قد يملك قصة أو منتجًا أو نشاطًا، لكنه لا يملك بطاقة بسيطة تُظهر جاهزيته وحدوده دون وعود مبالغ فيها.
3. **للمكان والجهة المحلية:** يمكن أن تتحول الزيارة إلى تصوير عشوائي أو ضغط على البيوت والمواقع الحساسة، من دون معرفة واضحة بالمسؤوليات والمنفعة المحلية.

## 2. المستخدمون والعملاء الأوائل

| الفئة | حاجتها العملية | ما لا نفترضه |
|---|---|---|
| الزائر المحلي أو الخارجي | قصة واضحة، مدة، وصول، حدود، وخطة يوم | لا نفترض استعداده للدفع أو الزيارة |
| العائلة | تجربة مفهومة وآمنة وغير متطفلة | لا نفترض وجود خدمة إشراف أو مسار مهيأ |
| صاحب تجربة أو منتج محلي | بطاقة عرض، ملف جاهزية، وطلب اهتمام منظم | لا نفترض أنه شريك أو أن سعره وتوافره مؤكدان |
| المرشد أو الراوي المحلي | طريقة لحماية المعرفة وإظهارها بموافقته | لا نفترض حقنا في نشر قصته أو صورته |
| السكان وأصحاب الأرض | احترام الخصوصية والمرور والتصوير وحق الانسحاب | لا نفترض أن المكان العام يساوي حق دخول أو تصوير |
| البلدية أو المجلس المحلي | بطاقة قابلة للمراجعة توضح السلامة والملكية والحدود | لا نفترض رعاية أو ملكية بيانات أو حجزًا |
| الجهة السياحية أو الثقافية | جواز جاهزية وأدلة وفجوات قبل الإدراج الرسمي | لا نفترض اعتمادًا أو تمويلًا |
| الإعلام وWordPress | قصة جذابة تفصل الرواية عن الواقعة وتعرض التحديث | لا نفترض أن المقال إعلان حجز |

## 3. الوعد والقيمة

### للزائر

> **اكتشف العيزرية ببطء، واعرف ما هو مؤكد وما يحتاج تحققًا، وابنِ يومك دون أن تستهلك المكان.**

### لصاحب التجربة

> **حوّل ما تعرفه أو تقدمه إلى بطاقة واضحة تُظهر القصة والجاهزية والفجوة التالية، دون أن تضطر إلى ادعاء ما لم يثبت.**

### للجهات المحلية والثقافية

> **احصل على طبقة مراجعة خفيفة قبل أن تتحول القصة إلى مسار عام أو حجز أو وعد رسمي.**

## 4. الحل المقترح

تتكون SENSE من ثلاث طبقات متصلة:

### طبقة القصة والإعلام

قصص وتقارير WordPress تقدم المكان كحياة وذاكرة وثقافة، لا كقائمة معالم. المقال الرئيسي هو: [العيزرية ليست محطة عبور: ماذا يرى الزائر حين تتوقف الرحلة؟](../wordpress/SENSE-AL-EIZARIYA-FEATURE-NOT-A-STOP.md).

### طبقة المسارات العامة

GitHub Pages يعرض مسارات قصيرة وجواز رحلة وخطة يوم. يقرأ الموقع بياناته من [`tourism/data/routes.json`](../../tourism/data/routes.json)، ويعرض لكل مسار مصدرًا، وحالة وصول، وحالة حجز، وأدلة مطلوبة.

### طبقة الجاهزية والمراجعة

SENSE Experience وLaunchpad يساعدان صاحب التجربة على إعداد ملف، ودرجة إرشادية، وفجوات، ومخرجات قابلة للتحرير. هذه الدرجة ليست اعتمادًا أو شهادة.

## 5. الحل البديل الحالي

يستخدم الزائر عادةً مزيجًا من:

- بحث عام وخرائط.
- صفحات التواصل الاجتماعي.
- الاتصال المباشر أو السؤال الشفهي.
- زيارات دينية أو تاريخية مختصرة.
- مدونات وصور متفرقة.
- قوائم أماكن لا تميز دائمًا بين الموثق والترويجي.

هذه البدائل قد تؤدي وظيفة الاكتشاف، لكنها لا تجمع في بطاقة واحدة: القصة، المصدر، الوصول، الحالة، الحجز، وحقوق المكان.

## 6. قنوات الوصول

| القناة | الوظيفة |
|---|---|
| WordPress | بناء الاهتمام والثقة عبر قصة أو تقرير قابل للقراءة والمشاركة |
| GitHub Pages | تجربة عامة سريعة ومفتوحة للزائر وبطاقة الحالة |
| SENSE Experience | تجهيز أصحاب التجارب والمراجعين |
| مقابلات محلية قصيرة | تصحيح الفرضيات وتحديد الأدلة الناقصة |
| حزم موجهة للبلدية أو الجهة السياحية | مراجعة مسؤوليات وسلامة وإتاحة دون ادعاء شراكة |
| إنفوجرافيك وميثاق الزائر | تحويل السلوك المسؤول إلى رسالة قابلة للمشاركة |

## 7. العلاقة مع المستخدم

العلاقة الأولى ليست حجزًا فوريًا، بل **شفافية وتعلم تدريجي**:

1. يقرأ الزائر قصة.
2. يفتح بطاقة مسار.
3. يرى ما نعرفه وما نحتاج إلى التحقق منه.
4. يضيف المسار إلى خطة يوم.
5. ينشئ مسودة اهتمام فقط إذا كانت التجربة مناسبة.
6. لا يتحول الطلب إلى حجز إلا بعد وجود مضيف وسعة وسعر ووصول وسلامة ووسيلة تواصل قابلة للمراجعة.

## 8. الموارد والقدرات الأساسية

- مستودع GitHub مركزي.
- GitHub Pages للنشر العام.
- `routes.json` كعقد بيانات بين المحتوى والواجهة.
- واجهة `app.js` ديناميكية لعرض المسارات وجواز الرحلة.
- سجل فرضيات أصحاب المصلحة.
- جواز جاهزية المشروع السياحي.
- Launchpad وواجهات صاحب التجربة والمراجع.
- قصص وتقارير WordPress.
- نظام مصادر وحالات ثقة ووصول وحجز.
- اختبارات JavaScript وTypeScript وبناء GitHub Actions.

## 9. الأنشطة الأساسية

1. تحويل كل ادعاء إلى مصدر أو فرضية واضحة.
2. اختبار بطاقة المسار مع زوار محدودين.
3. إجراء مقابلات قصيرة مع مضيفين وسكان وجهة مراجعة.
4. قياس وضوح المدة والصعوبة والوصول والحجز.
5. مراجعة الخصوصية وحق التصوير وملكية المكان.
6. تحديث `routes.json` بدل تعديل المحتوى عشوائيًا.
7. إنتاج قصة WordPress من الأدلة المتاحة فقط.
8. فتح مسار تشغيلي أو حجز فقط بعد اجتياز بوابة القرار.

## 10. الشركاء المحتملون

هذه قائمة جهات يمكن طلب مراجعتها، وليست قائمة شركاء مؤكدين:

- البلدية أو المجلس المحلي.
- مديرية أو وزارة السياحة والآثار.
- مؤسسات ثقافية وتعليمية.
- مرشدون وأصحاب تجارب ومنتجات محلية.
- مزودو النقل والإتاحة.
- باحثون أو جامعات.
- برامج ابتكار أو تمويل.

لا تُنسب لأي جهة شراكة أو موافقة إلا بعد دليل مكتوب ومالك قرار معروف.

## 11. مؤشرات التعلم والنجاح

لا نستخدم أرقامًا افتراضية على أنها نتائج. تبدأ القياسات التالية من الصفر بعد إطلاق أدوات القياس المناسبة:

| المؤشر | الحد الأدنى للحدث | القرار الذي يدعمه |
|---|---|---|
| فهم بطاقة المسار | سؤال قصير بعد القراءة | تعديل العنوان أو الوصف أو التحذير |
| استخدام الفلتر | اختيار مدة/صعوبة/نوع تجربة | تحسين بنية المسارات |
| إنشاء خطة يوم | إضافة مسار واحد أو أكثر | معرفة المسارات ذات الجاذبية الأولية |
| وضوح حالة الحجز | قدرة الزائر على وصف ما هو متاح وغير متاح | منع وعود مضللة |
| اكتمال ملف المضيف | حقول لها مصدر أو إجابة واضحة | تحديد فجوة المقابلة التالية |
| احترام المكان | ملاحظات أو اعتراضات موثقة | تعديل الموقع أو إخفاء التفاصيل |
| المنفعة المحلية | وجود مستفيد وطريقة منفعة قابلة للشرح | إبقاء المسار أو تعديله أو إيقافه |
| الإحالة الرسمية | مراجعة أو إحالة من جهة مناسبة | إعداد حزمة شراكة، دون افتراض قبول |

## 13. نموذج الإيرادات والاقتصاد

لا يوجد نموذج إيرادات مثبت حتى الآن. الخيارات التي يمكن بحثها لاحقًا:

- اشتراك أو خدمة تجهيز لأصحاب التجارب.
- رسوم إعداد ملف أو قصة بعد موافقة صاحبها.
- شراكة مع برنامج ثقافي أو سياحي.
- خدمات مراجعة محتوى وإتاحة وسلامة.
- رعاية تجربة محددة بنطاق واضح.

لا يجوز وضع سعر أو طلب دفع أو وعد بتحويل مالي قبل اختبار الطلب ووجود خدمة ومالك تشغيل.

## 14. المخاطر والحدود

- تحويل قصة شعبية إلى حقيقة تاريخية دون مصدر.
- نشر موقع خاص أو حساس دون موافقة.
- تصوير السكان أو الأطفال دون إذن.
- استعمال “موثق” أو “معتمد” دون دليل.
- عرض حجز غير تشغيلي.
- الخلط بين بيانات السياحة وبيانات البلديات أو البلاغات.
- اعتبار عدد الزيارات دليلًا على الأثر الاقتصادي.
- نشر بيانات شخصية في GitHub أو WordPress.
- استخدام صعوبة أو إتاحة غير مقاسة ميدانيًا.
- استنزاف الفريق في بناء واجهات قبل إجراء مقابلات واختبارات حقيقية.

## 15. بوابة القرار

يبقى المسار **تحريريًا أو قيد التحقق** حتى تتوفر، بشكل مؤرخ وقابل للمراجعة:

- صاحب خدمة أو مضيف معلوم.
- نقطة لقاء أو وصف وصول مناسب.
- سعة وزمن وسعر أو طريقة تسعير.
- سياسة إلغاء أو عدم توفر.
- مراجعة سلامة.
- حالة ملكية وحق تصوير.
- وسيلة تواصل.
- منفعة محلية قابلة للشرح.

ولا ينتقل المسار إلى “حجز تشغيلي” أو “اعتماد رسمي” بمجرد ارتفاع عدد القراءات أو النقرات.

## 16. خطة التحول من الفكرة إلى المنتج

### المرحلة 1 — الآن

- ربط المسارات بـ `routes.json`.
- إضافة تصفية حسب المدة والصعوبة ونوع التجربة.
- إظهار بطاقة الثقة بوضوح.
- توثيق حالة كل مسار.

### المرحلة 2 — التعلم الميداني

- اختبار البطاقات مع زوار محدودين.
- إجراء ثلاث مقابلات قصيرة: صاحب تجربة، شخص من المجتمع، وجهة مراجعة.
- تسجيل النتائج دون بيانات شخصية.
- تحديث الفرضيات والبطاقات.

### المرحلة 3 — حزمة المراجعة

- تصدير بطاقة لمسار محدد.
- تجهيز نسخة مناسبة للبلدية أو الجهة السياحية.
- إعداد نسخة WordPress محدثة فقط إذا تغيرت معلومة جوهرية.

### المرحلة 4 — تشغيل محدود

- فتح تجربة واحدة فقط إذا استوفت بوابة القرار.
- اختبار طلب اهتمام أو حجز يدوي.
- تسجيل السعة والاستجابة والإلغاء والرضا.
- عدم توسيع المسارات قبل إغلاق فجوة التشغيل الأساسية.

## 17. القرار الحالي

**قرار المنتج:** لا نضيف المزيد من القصص أو المسارات قبل أن تصبح البطاقات قابلة للتصفية والفهم والمراجعة.

**قرار الإعلام:** WordPress يروي لماذا يهم المكان؛ GitHub Pages يوضح ماذا نعرف الآن؛ ملف Canvas وسجل الفرضيات يوجهان ما يجب اختباره لاحقًا.

**قرار التقنية:** `routes.json` هو المصدر العام الموحد، و`app.js` يستهلكه ديناميكيًا. أي نظام حجز حقيقي مؤجل إلى ما بعد وجود مضيف ودليل تشغيل.

**النتيجة المستهدفة:** منصة صغيرة صادقة وقابلة للمراجعة أفضل من منصة كبيرة توحي بحجوزات وشراكات غير موجودة.
