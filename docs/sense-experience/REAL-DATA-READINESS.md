# بوابة قبول بيانات مزودي الخدمات الحقيقية

## الحالة الحالية

المخطط والترحيل وAPI متوافرة في المستودع، لكن الخدمة لا تبدأ في وضع استقبال بيانات حقيقية ما لم يتوفر متغير اتصال مستقل وتفعيل صريح. حتى عند تشغيلها، تبقى إجراءات المراجعة محجوبة إلى أن يستبدل سياق المراجع الفارغ بآلية دخول وأدوار حقيقية.

| البوابة | الحالة | المطلوب قبل الفتح |
|---|---|---|
| مخطط مستقل | جاهز للمراجعة | تطبيق الترحيل على قاعدة SENSE Experience منفصلة. |
| واجهة API | موجودة ومقفلة افتراضيًا | `SENSE_EXPERIENCE_DATABASE_URL` مستقل و`SENSE_EXPERIENCE_ACCEPT_REAL_DATA=true` بعد اعتماد المراجعة. |
| مراجعة بشرية | عقد وإجراءات محمية وهوية وأدوار مستقلة موجودة | مزود OAuth/OIDC مستقل يتحقق من الجلسة على الخادم ويطابق سجل هوية مفعّلًا ودورًا نشطًا. |
| سجل قرار | جدول قرار وجدول أحداث موجودان | اختبار تكامل على القاعدة وسجل احتفاظ/حذف معتمد. |
| واجهة عامة | غير مفعلة | تجربة محدودة مع مزودين وافقوا صراحة ومراجعة خصوصية. |

## قواعد التشغيل

لا يكتب فريق التشغيل `SENSE_EXPERIENCE_DATABASE_URL` في ملف ملتزم أو رسالة. ولا يستخدم عنوان قاعدة Urban‑Sense كبديل. يجب تطبيق ترحيل `drizzle/migrations/0000_glossy_hemingway.sql` على قاعدة مخصصة للخدمة، ومراجعته من مسؤول قاعدة البيانات قبل تفعيل API.

لا يكفي ضبط `SENSE_EXPERIENCE_ACCEPT_REAL_DATA=true` لفتح المراجعة؛ هذا المتغير يفتح نقطة استقبال الطلب فقط. تبقى طلبات قراءة القائمة والقرار مرفوضة حتى يضاف مصدر هوية يثبت دور `reviewer` أو `administrator` في سياق tRPC. محلل الهوية الحالي رافض افتراضيًا ويتجاهل كل ترويسات العميل، لذلك لا يمكن انتحال دور مراجع قبل ضبط مزود هوية مستقل.
