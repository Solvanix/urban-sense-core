# نموذج الأعمال وخطة التطوير الشاملة لمنظومة SENSE

**تاريخ الإصدار:** 12 سبتمبر 2026

## 1. الغرض

هذه الوثيقة تحول منظومة SENSE من مجموعة تطبيقات ووثائق متجاورة إلى **محفظة منتجات مترابطة بحدود واضحة**. المقصود بـ«نموذج الأعمال» هنا ليس شعارًا تسويقيًا، بل نظام كامل يصف المشكلة، المستخدم، القيمة، طريقة التشغيل، الإيراد المحتمل، البيانات، الشراكات، المخاطر، بوابات الإطلاق، ومؤشرات القرار لكل مسار.

لا تعني هذه الخطة أن كل المسارات أصبحت خدمات إنتاجية. التصنيف الصريح هو جزء من المنتج نفسه: ما هو منشور، وما هو قابل للبناء، وما هو MVP ثابت، وما يحتاج مالك تشغيل أو موافقة أو بنية خلفية قبل فتحه.

## 2. الأطروحة الموحدة

تساعد SENSE المجتمعات المحلية والمزودين والجهات البلدية على تحويل **المعلومة غير المنظمة إلى فعل موثق وقابل للمراجعة**. وتظهر هذه الأطروحة في أربعة مسارات مستقلة:

| المسار | المشكلة | القيمة المقترحة | المشتري أو الممول المحتمل | الحالة |
|---|---|---|---|---|
| Urban‑Sense | البلاغات تضيع بين الهاتف والرسائل والملفات، ولا توجد دورة إغلاق موثقة. | بلاغ عربي، إسناد محكوم، دليل قبل/بعد، تدقيق وإغلاق. | بلدية أو جهة خدمية أو برنامج مدني. | نواة وظيفية في بيئة عرض؛ تحتاج نشرًا تملكه الجهة. |
| SENSE Experience | معلومات المزودين والوجهات غير موثقة، ويصعب التمييز بين الوصف والادعاء. | جاهزية مزود، أدلة وادعاءات، مراجعة بشرية، نشر انتقائي. | مزودون، شريك سياحي، جهة تنمية محلية. | نواة مستقلة غير منشورة. |
| Pizza hot / Commerce Pilot | المزود المحلي يحتاج واجهة كتالوج وطلب واضحة قبل بناء متجر كامل. | كتالوج، مساعد مقيد بالمصدر، سلة، إحالة للمراجعة البشرية. | المزود نفسه أو شريك تشغيل محلي. | MVP ثابت منشور؛ ليس متجرًا إنتاجيًا. |
| SENSE Portal & Initiatives | الجمهور لا يعرف أي مدخل يستخدم ولا حالة كل مبادرة. | فهرس صادق يربط المنتجات والمبادرات والوثائق. | أداة اكتشاف وشراكات؛ ليست مصدر الإيراد بذاتها. | منشور كواجهة توجيه. |

## 3. شرائح العملاء والمستفيدين

### 3.1 الجهات البلدية

تحتاج إلى إدارة دورة البلاغات، تقليل زمن الإقرار والإسناد، وإثبات الإغلاق. لا يبدأ البيع بتقنية عامة، بل بتحديد نطاق بلدي، جهة مالكة، فريق عمليات، سياسة احتفاظ، واستضافة مناسبة.

### 3.2 مزودو الخدمات والتجارب

يحتاج المزود إلى ملف واضح لا يبالغ في وعوده، ومسار يثبت الجاهزية والمكونات والوصول وساعات العمل قبل عرضه للعامة. لا يحق للمنظومة إنشاء مزود أو تقييم أو شهادة اصطناعية لملء الفراغ.

### 3.3 المشترون والزوار

يحتاجون إلى معلومات قابلة للفهم ومصدرها واضح، وقنوات طلب أو إحالة لا توهم بأن الدفع أو التوصيل متاحان إذا لم يكونا مفعّلين. واجهة Pizza hot الحالية تثبت هذا المبدأ: المنتجات بلا سعر موثق لا تدخل السلة.

### 3.4 الشركاء والمبادرات

يشمل ذلك مبادرات السياحة الشاملة، التخطيط الحضري، الإتاحة، أرض كنعان، ومركز التصنيع الرقمي المقترح. دورها في النموذج هو إنتاج أثر وشراكات وتجارب قابلة للتوثيق، لا تحويل كل فكرة إلى صفحة «منتج حي» بلا مالك تشغيل.

## 4. نموذج القيمة والتشغيل

تتكون المنظومة من سلسلة ثقة مشتركة:

1. **التقاط:** بلاغ، طلب اهتمام، بيانات مزود، أو سؤال مستخدم.
2. **تصنيف:** تحديد المجال والمالك وحساسية البيانات.
3. **إثبات:** صورة، مستند، مصدر، موافقة، أو حقيقة قابلة للتحقق.
4. **مراجعة:** قرار بشري أو دور مفوض، مع سجل تدقيق.
5. **نشر انتقائي:** لا ينشر للعامة إلا العقد العام المسموح به.
6. **فعل:** إغلاق بلاغ، تحديث بطاقة، إحالة طلب، أو بدء شراكة.
7. **تعلم:** مقياس واضح وشكوى وتحسين وإعادة مراجعة.

## 5. خطوط الإيراد المحتملة

هذه خيارات تحتاج قرارًا تجاريًا وقانونيًا، وليست إيرادات حالية:

| الخط | طريقة التسعير المحتملة | شرط الصلاحية |
|---|---|---|
| Urban‑Sense للبلديات | اشتراك خدمة أو عقد تنفيذ ودعم حسب النطاق | جهة مالكة، SLA، استضافة، حماية بيانات، ودعم. |
| SENSE Experience | اشتراك مزود، خدمة مراجعة، أو رعاية وجهة | موافقة المزود، سياسة claims، ومراجعون مستقلون. |
| Commerce Pilot | رسم خدمة أو اشتراك متجر أو عمولة معلنة | كيان قانوني، طلبات حقيقية، دفع، إرجاع، ضرائب وتنفيذ. |
| مبادرات الإتاحة والأثر | منح، شراكات، عقود أثر أو رعاية | تعريف مقياس الأثر، موافقات، وعدم استغلال قصص المستفيدين. |
| تنفيذ وتكامل | رسوم إعداد وربط وتدريب | نطاق عمل مكتوب وملكية واضحة للكود والبيانات. |

لا يجوز تسجيل GMV أو MRR أو عمولة أو معدل تحويل قبل وجود معاملات فعلية ومصدر قياس قابل للتدقيق.

## 6. حدود البيانات والتكامل

كل تطبيق يملك هويته وقاعدته وسجله. التكاملات الصحيحة تكون عبر عقود محدودة:

| من | إلى | العقد المسموح | الممنوع |
|---|---|---|---|
| SENSE Experience | الموقع العام | بطاقة مزود منشورة وموافق عليها | تمرير ملف المراجعة أو بيانات الاتصال الخاصة. |
| SENSE Experience | Commerce Pilot | عنصر منشور، اسم، وصف، حالة، ومعرّف عام | قراءة قاعدة المراجعة أو نشر تلقائي. |
| Pizza hot | الموقع العام | رابط ومعلومات عامة مؤكدة | اعتبار السلة الحالية نظام طلب مركزي. |
| Urban‑Sense | بوابة SENSE | حالة المنتج ورابط عام | مشاركة بلاغات المواطنين أو أدوار البلدية. |
| المبادرات | أي تطبيق | مخرجات عامة ومقاييس مجهّلة عند الحاجة | نقل بيانات حساسة أو صور دون موافقة. |

## 7. خارطة المنتج التنفيذية

### المرحلة A — الأساس المشترك

تثبيت سجل المنتجات، حالات الحقيقة، حدود البيانات، فحوص الأسرار، بنية صفحات GitHub Pages، وقالب توثيق لكل تطبيق.

**معيار القبول:** يستطيع أي شخص معرفة ما يعمل وما لا يعمل من المستودع والروابط دون الاعتماد على شرح شفهي.

### المرحلة B — Urban‑Sense مستقل

اختيار خادم تملكه الجهة، تشغيل Docker وMySQL، تفعيل هوية مناسبة، تخزين أدلة، نسخ احتياطي، نطاق وTLS، مراقبة، واختبار قبول مع نطاق بلدي محدود.

**معيار القبول:** بلاغ حقيقي تجريبي يمر من التقديم إلى الإغلاق مع صلاحيات وسجل تدقيق ونسخ احتياطي.

### المرحلة C — SENSE Experience محدود

نشر API والواجهة في بيئة مستقلة، تطبيق الترحيلات، تفعيل هوية المراجعين، سياسة الخصوصية والاحتفاظ والحذف، ثم استقبال مزود واحد بموافقته.

**معيار القبول:** ملف مزود حقيقي خاص، ادعاء مع دليل، قرار مراجع، وبطاقة عامة محدودة إن تمت الموافقة.

### المرحلة D — Commerce Pilot

تطوير Pizza hot من صفحة ثابتة إلى كتالوج مملوك مع API طلبات، مخزون أو حالة توفر، موافقة مزود، إشعارات، ثم بوابة دفع وتنفيذ بعد اعتماد الكيان القانوني.

**معيار القبول:** طلب تجريبي حقيقي قابل للتتبع من القبول إلى التنفيذ والإلغاء وخدمة العملاء، دون كشف أسرار أو بيانات حساسة.

### المرحلة E — المبادرات والأثر

إنشاء سجل مبادرات يربط كل مبادرة بمالك، مستفيد، نشاط، مخرج، مقياس، ومصدر تمويل أو شراكة. تندرج السياحة الشاملة والتخطيط للعيزرية ضمن برامج لا تُعرض كخدمات تشغيلية قبل وجود شريك وبيانات وموافقة.

**معيار القبول:** مبادرة واحدة لها موافقات ومقياس قبل/بعد وخطة تحديث ومسؤول واضح.

## 8. مؤشرات القرار

لا نستخدم مؤشرات زائفة لمجرد أن الواجهة جميلة. لكل مسار لوحة قياس منفصلة:

- Urban‑Sense: زمن الإقرار، زمن الإسناد، نسبة الإغلاق بدليل، إعادة الفتح، رضا المواطن، وحوادث الصلاحيات.
- SENSE Experience: طلبات الاهتمام، اكتمال الملف، زمن المراجعة، نسبة الادعاءات المدعومة، وقرارات الرفض.
- Commerce Pilot: منتجات مؤكدة، طلبات مقبولة، زمن الرد، نسبة الإلغاء، تكلفة التنفيذ، ونسبة الطلبات غير المكتملة.
- المبادرات: مشاركة فعلية، مخرجات مكتملة، أثر قبل/بعد، شكاوى، ونسبة البيانات ذات الموافقة.
- المنظومة: روابط تعمل، فحوص CI ناجحة، أسرار مكشوفة، زمن تحديث الوثائق، وعدد الادعاءات غير الموثقة.

## 9. مخاطر يجب ألا نخفيها

- خلط العرض الاستكشافي بالمنتج التشغيلي.
- نسخ بيانات المتجر القديم أو بيانات مزودين دون ملكية أو موافقة.
- إطلاق دفع أو طلبات قبل كيان قانوني وسياسة إرجاع وخدمة عملاء.
- مشاركة قاعدة بيانات أو حسابات بين البلدية والمزودين.
- استخدام صور أو نماذج أو كود طرف ثالث دون تحقق من الرخصة.
- ادعاء الإتاحة أو السياحة الشاملة دون اختبار تشاركي مع المستفيدين.
- تسريب مفاتيح Convex أو رموز الذكاء الاصطناعي عبر التصدير أو GitHub.

## 10. قرارات مطلوبة من المالك لاحقًا

1. اختيار أول منتج مدفوع أو ممول: Urban‑Sense أم SENSE Experience أم Commerce Pilot.
2. تحديد الكيان القانوني ومالك العقود والبيانات.
3. اعتماد اسم العلامة والنطاق والبريد المهني.
4. تحديد أول بلدية أو مزود أو مبادرة يمكن الحصول على موافقته فعليًا.
5. اختيار الخادم والاستضافة والميزانية التشغيلية.
6. اعتماد سياسة الخصوصية والاحتفاظ والحذف.
7. اعتماد حدود استخدام الذكاء الاصطناعي والمراجعة البشرية.
