# خريطة تسليم نظام SENSE للفريق

**مصدر النظام المعتمد:** [`Solvanix/urban-sense-core`](https://github.com/Solvanix/urban-sense-core)
**الغرض:** تمكين فريق SENSE من معرفة أين توجد ملفات النظام، ومن يجهز كل طبقة، وكيف تنشأ نسخة عرض مستقلة من دون نقل أسرار أو بيانات حقيقية إلى GitHub.

> لا يحتاج الفريق إلى طلب ملفات من Manus لبناء النظام. الملفات البرمجية المعتمدة موجودة في المستودع المركزي. Manus هو رابط عرض مؤقت، وليس مستودع المصدر أو مكان تسليم المنتج النهائي.

## أولًا: أين توجد الملفات؟

| ما الذي تريد الوصول إليه؟ | مكانه في المستودع | ماذا يفعل؟ | من يحتاجه؟ |
|---|---|---|---|
| بوابة SENSE وUrban‑Sense | `apps/web/` | التطبيق البلدي والبوابة الموحدة والواجهة والخادم والمخطط والاختبارات | المطورون ومالك النشر |
| SENSE Experience | `apps/sense-experience/` | تطبيق مستقل لمسار مزودي الخدمات والمراجعة البشرية | فريق المنتج والمطورون عند إطلاقه المستقل |
| الفهرس العام | `public-index/index.html` | موقع GitHub Pages ثابت يشرح المسارات والحالات | الجمهور والفريق والشركاء |
| فهرس الجذر المرجعي | `INDEX.html` و`INDEX.md` | خريطة بصرية ونصية للمستودع | كل أعضاء الفريق |
| وثائق الحوكمة والتشغيل | `docs/` | القرارات والحدود وخارطة المنتج ودليل التشغيل | الإدارة والفريق التقني |
| إعداد خادم Urban‑Sense | `apps/web/Dockerfile` و`apps/web/compose.yaml` و`apps/web/ops/` | بناء التطبيق وتشغيل MySQL محليًا لعرض جديد | مسؤول الخادم أو المطور المفوض |
| قالب إعداد التشغيل | `apps/web/.env.runtime.example` | أسماء الإعدادات المطلوبة بلا قيم حقيقية | مسؤول الخادم فقط |
| جودة المصدر | `.github/workflows/` وملفات الاختبار في كل تطبيق | فحوص GitHub Actions والنوع والاختبارات والبناء | المطورون والمراجعون |

## ثانيًا: ما الذي يرسله صاحب المشروع إلى الفريق؟

لا توجد حزمة ملفات خاصة تُرسل بالواتساب أو البريد. الإجراء الصحيح هو منح كل عضو **الوصول المناسب** ثم استخدام المصدر نفسه.

| الشخص | ما يحصل عليه | ما لا يحصل عليه افتراضيًا |
|---|---|---|
| عضو المنتج أو المصمم | رابط المستودع والفهرس العام ووثائق المنتج | كلمات مرور الخادم أو قاعدة البيانات |
| مطور واجهة أو خادم | نسخة من المستودع عبر `git clone` وصلاحية عمل أو Pull Request بحسب دوره | أسرار الإنتاج، ما لم يكن مسؤول تشغيل مخولًا |
| مسؤول نشر/DevOps | المستودع + وصول الخادم + ملف إعداد التشغيل الحقيقي على الخادم | حق نقل الأسرار إلى GitHub أو مشاركتها في المحادثات |
| عضو بلدية أو مراجع | حساب منفصل داخل التطبيق عند إطلاق بيئته | وصول GitHub الإداري أو خادم الإنتاج |
| الجمهور | رابط GitHub Pages والفهرس العام فقط | كتابة الكود أو دخول التطبيق أو البيانات |

## ثالثًا: ما الذي يفعله المطور في أول يوم؟

### لاستكشاف الكود وبنائه محليًا

```bash
git clone https://github.com/Solvanix/urban-sense-core.git
cd urban-sense-core/apps/web
pnpm install
pnpm check
pnpm test
pnpm build
```

لا يحتاج هذا المسار إلى بيانات مواطنين أو قاعدة بيانات إنتاج. هو يثبت أن التطبيق يبنى وأن الاختبارات تعمل.

### لتشغيل عرض مستقل على خادم يملكه الفريق

ينفذ مسؤول الخادم الخطوات التالية على الخادم، وليس في جهاز كل عضو عادي:

```bash
git clone https://github.com/Solvanix/urban-sense-core.git
cd urban-sense-core/apps/web
cp .env.runtime.example .env.runtime
```

ثم يملأ مسؤول الخادم **محليًا فقط** ملف `.env.runtime` بالقيم الفعلية، مثل كلمات مرور MySQL وسر الجلسة وعنوان التطبيق. بعد ذلك:

```bash
bash ops/bootstrap-server.sh
```

ينشئ الأمر قاعدة MySQL فارغة للعرض ويشغّل التطبيق في Docker. فحص الصحة يصبح متاحًا على:

```text
http://عنوان-الخادم:3000/healthz
```

## رابعًا: أين تحفظ القيم الحقيقية والبيانات؟

| المادة | مكانها الصحيح | من يحفظها؟ |
|---|---|---|
| كلمات مرور قاعدة البيانات ومفاتيح OIDC وسر الجلسة | ملف `.env.runtime` على الخادم أو مدير أسرار تملكه الجهة | مسؤول الخادم والمالك المفوضان فقط |
| قاعدة بيانات العرض أو الإنتاج | خدمة MySQL على الخادم أو قاعدة مُدارة باسم الجهة | مسؤول قاعدة البيانات |
| صور الأدلة والمرفقات الحقيقية | تخزين كائنات باسم الجهة عند إطلاق الإنتاج | مسؤول التخزين والسياسات |
| النسخ الاحتياطية | نظام نسخ احتياطي منفصل ومشفر خارج Git | المالك ومسؤول التشغيل |
| الكود والوثائق العامة | GitHub | فريق التطوير والجمهور بحسب الرؤية العامة |

**قاعدة واحدة للفريق:** لا يرسل أحد كلمة مرور أو مفتاحًا إلى Issue أو Pull Request أو تعليق أو محادثة عامة. لا يرفع ملف `.env.runtime` إلى GitHub؛ قاعدة التجاهل تمنع ذلك عمدًا.

## سادسًا: ما الذي يلزم قبل تسمية النظام «إنتاجًا رسميًا»؟

1. اختيار خادم أو استضافة باسم الجهة وتشغيل حزمة Docker عليه بنجاح.
2. إعداد نطاق رسمي وHTTPS بعد اعتماد الاسم، من دون شراء أو ربط قبل قرار المالك.
3. إنشاء مزود هوية OIDC مملوك للجهة وتعيين إعداداته خارج Git.
4. إنشاء قاعدة MySQL إنتاجية ونسخ احتياطي وسياسة وصول.
5. نقل Urban‑Sense تدريجيًا من بيئة العرض إلى هذا الخادم بعد اختبار فريق داخلي.
6. نشر SENSE Experience لاحقًا كخدمة مستقلة بقاعدة وهوية ومراجع بشري مستقلين.

هذه هي طريقة تجهيز الفريق: **المستودع العام يوزع النظام، الأدوار تحدد من يملك الوصول، والخادم يملك الإعدادات والبيانات الحقيقية.**
