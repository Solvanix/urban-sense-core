# معمارية منظومة SENSE داخل مستودع واحد

## المبدأ

المستودع [`Solvanix/urban-sense-core`](https://github.com/Solvanix/urban-sense-core) هو السجل التنفيذي المركزي. لا يعني ذلك تطبيقًا واحدًا أو قاعدة بيانات واحدة؛ بل يعني أن قرارات التصميم والكود والاختبارات والمراجعات تعيش في مكان واحد، بينما تبقى التطبيقات قابلة للنشر والاختبار والتوسع بصورة مستقلة.

| الطبقة | التطبيق أو الحزمة | الجمهور | حد البيانات |
|---|---|---|---|
| بلاغات مدنية | `apps/web` — Urban‑Sense | مواطنون وموظفو بلديات وفرق ميدانية. | قاعدة وتقارير وأدلة وسجل تدقيق مدني مستقل. |
| تجربة مزود سياحي | `apps/sense-experience` | مزودون ومراجعون وزوار. | قاعدة ملفات مزودين وخدمات وقرارات مراجعة مستقلة. |
| الموقع العام | `apps/public-site` — موجة لاحقة | جمهور SENSE والشركاء. | محتوى عام وروابط فقط؛ لا بيانات تشغيل أو حسابات. |
| التجارة | `apps/commerce` — موجة لاحقة | مشترون ومزودون ومديرو كتالوج. | كتالوج وطلبات ودفع/لوجستيات معزولة. |
| أدوات الإتاحة | `apps/accessibility-tools` أو `packages/accessibility` — موجة لاحقة | مستخدمون ومحررون ومطورون. | تفضيلات مستخدم واعية، بلا بيانات بلدية أو مزودين خاصة. |
| عقود وتصميم مشترك | `packages/contracts` و`packages/design-system` — بعد تثبيت التطبيقين الأولين. | كل التطبيقات. | أنواع عامة ومكونات إمكانية وصول، لا أسرار أو جداول تشغيلية. |

## التكامل الصحيح

تتكامل التطبيقات عبر عقود صغيرة موثقة. مثال: عندما تعتمد منصة التجربة ملف مزود، يمكنها لاحقًا نشر نسخة عامة مصغرة تحمل المعرف العام واسم العلامة والوصف الموافق عليه وحالة التحقق. إذا ظهر عرض في المتجر مستقبلًا، لا يحصل المتجر على بيانات الاتصال الخاصة أو محادثات المراجعة؛ بل على عقد «عنصر منشور» محدود.

لا تقرأ منصة السياحة بلاغات المواطنين أو أدلتهم أو حالات تشغيل البلديات. ولا يقرأ Urban‑Sense أو يعدل مزودي السياحة أو الطلبات التجارية. يشارك الجميع هوية بصرية وإرشادات إتاحة وعقود واجهة عامة، لا قواعد بيانات أو أدوار داخلية.

## موجات التنفيذ

| الموجة | ما يبنى | معيار القبول | ما يؤجل عمدًا |
|---|---|---|---|
| 1 | إتمام انضمام مزود السياحة ومراجعته وحفظه في قاعدة مستقلة. | مسار كامل بلا ادعاءات أو بيانات مزودين وهمية. | حجوزات، دفع، أو عرض مزودين حقيقيين قبل الموافقة. |
| 2 | موقع عام خفيف يشرح المنتجات ويوجه لكل تطبيق. | روابط صادقة وحالة منتج واضحة وإتاحة أساسية. | لوحة تشغيل أو حسابات موحدة لمجرد التجميع. |
| 3 | نواة تجارة داخلية: كتالوج ومراجعة عناصر ومخزون وطلب. | فصل المدفوعات والبيانات الحساسة، واختبارات عقد. | بطاقات أو شحن أو توافر حي قبل شريك حقيقي. |
| 4 | طبقة إتاحة مشتركة وأدوات تدقيق محتوى وواجهات. | فحوص لوحة المفاتيح والأسماء البرمجية والتباين واللغة. | ادعاء بناء قارئ شاشة بديل للأنظمة أو حل كل احتياجات الإعاقة دفعة واحدة. |
| 5 | تكاملات منشورة انتقائيًا بين التجربة والمتجر والموقع. | عقد API موثق وحالات رفض ومراجعة ومراقبة. | قواعد مشتركة أو نسخ غير مراقب للبيانات. |

## الحوكمة والجودة

كل تطبيق يملك `package.json` واختباراته وبناءه ونطاق CI الخاص به. يضيف GitHub Actions لاحقًا مهام موجهة بالمسار، بحيث لا يوقف تغيير الموقع العام تحقق تطبيق البلاغات، ولا يمر تغيير نطاقي بلا فحصه الخاص. وتبقى قرارات العزل أو العقود الجديدة في `docs/decision-records/`.

## المرجع

تُفصّل قواعد مزود السياحة في [حدود SENSE Experience](sense-experience/PRODUCT-BOUNDARIES.md)، بينما تبقى حدود Urban‑Sense في وثائق المعمارية والأمن الموجودة أصلًا في هذا المستودع.
