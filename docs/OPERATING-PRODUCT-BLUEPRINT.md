# خارطة التشغيل والمنتج لمنظومة SENSE

**حالة الوثيقة:** مرجع تشغيلي مقترح ومحدث حتى 18 أغسطس 2026.  
**المستودع المركزي:** [`Solvanix/urban-sense-core`](https://github.com/Solvanix/urban-sense-core).  
**قاعدة القراءة:** ما هو مكتوب **«قائم»** موجود في الكود أو البيئة الموثقة؛ وما هو مكتوب **«مقترح»** يحتاج قرارًا وتنفيذًا ولا يجوز عرضه للجمهور كخدمة متاحة.

> هذه الوثيقة لا تمثل استشارة قانونية أو ضريبية أو قوائم مالية. يراجع المحاسب والمحامي المحليان نموذج التسجيل، الضرائب، العقود، وسياسة الاحتفاظ قبل أي تعاقد أو تحصيل أو معالجة بيانات حقيقية.

## 1. الخلاصة التنفيذية: ماذا نملك الآن؟

المستودع ليس موقعًا واحدًا، بل **محفظة تطبيقات مستقلة** تحت حوكمة وكود وقرار معماري واحد. التطبيق البلدي Urban‑Sense هو التطبيق الوحيد المنشور للعامة حاليًا. أما SENSE Experience فهو تطبيق مستقل له واجهة عربية ومسار مزودين وخدمة وبيانات مستقلة في المصدر، لكن لا يملك بعد رابط إنتاج مستقل ولا يقبل بيانات مزودين حقيقية. المتجر، الموقع العام للعلامة، وأدوات الإتاحة أجزاء مقترحة من المحفظة، وليست تطبيقات مكتملة أو منشورة.[1]

| المسار | المنتج | الحالة الدقيقة | الرابط أو نقطة الدخول |
|---|---|---|---|
| `apps/web` | **Urban‑Sense** للبلاغات البلدية | قائم، مختبر، ومنشور على بيئة Manus. | [الموقع الحي](https://urbansense-dzfbcdz5.manus.space/) · [المصدر](https://github.com/Solvanix/urban-sense-core/tree/main/apps/web) |
| `apps/sense-experience` | **SENSE Experience** لمزودي الخدمات والتجارب | قائم في GitHub كنواة وواجهة تصور؛ غير منشور كرابط إنتاج مستقل؛ لا بيانات مزودين حقيقية. | [المصدر](https://github.com/Solvanix/urban-sense-core/tree/main/apps/sense-experience) |
| `apps/public-site` | موقع SENSE العام | **مقترح**؛ لا يوجد دليل حاليًا. | لا رابط |
| `apps/commerce` | المتجر العام متعدد المشاريع | **مقترح**؛ لا يوجد كود أو دفع أو طلبات. | لا رابط |
| `apps/accessibility-tools` أو `packages/accessibility` | طبقة وأدوات إتاحة | **مقترح**؛ بعض ممارسات الإتاحة موجودة داخل التطبيقات، لكن لا توجد حزمة مستقلة. | لا رابط |
| `packages/contracts` و`packages/design-system` | عقود وتصميم مشترك | **مقترح** بعد تثبيت التطبيقين الأولين. | لا رابط |

## 2. الصفحات والروابط الحالية

### 2.1 Urban‑Sense — التطبيق البلدي

هذا التطبيق محصور في البلاغات البلدية، ولا يحتوي سياحة أو متجرًا. صفحاته العامة الحالية تشمل:

| المسار | الجمهور | الوظيفة |
|---|---|---|
| `/` | الجمهور | تعريف المنصة ومسار البلاغ والدعوة إلى التجربة. |
| `/كيف-تعمل` | المواطنون والشركاء | شرح خطوات البلاغ والمراجعة والدليل والإغلاق. |
| `/للبلديات` | البلديات | شرح تشغيل البلاغات وضوابط الصلاحيات. |
| `/التجربة` | المشاركون في التجربة | توجيه صادق لمسار المشاركة التجريبي. |
| واجهات المواطن والعمليات المحمية | المواطنون والموظفون | تقديم بلاغ، متابعة حالة، مراجعة، إسناد، أدلة، تحقق، إغلاق وتقييم لاحق. |

دورة العمل الموجودة هي: **تقديم بلاغ → مراجعة → إسناد → أدلة ميدانية → تحقق مشرف → إغلاق → تقييم مواطن اختياري**، مع سجل تدقيق مرتبط بسلسلة SHA‑256. لا توجد بيانات تقييم مصطنعة؛ الحصول على أول تقييم حقيقي ما زال بندًا تشغيليًا في تجربة محدودة.[2]

### 2.2 SENSE Experience — التطبيق السياحي

الواجهة العامة والتشغيلية تعيشان في تطبيق منفصل كي لا تختلط بيانات الزوار والمزودين ببيانات المواطنين أو موظفي البلديات.

| المسار | الحالة | الوظيفة |
|---|---|---|
| `/` | قائم في الكود | بوابة «مكان · مسار · أثر» تشرح الفكرة من دون عرض مزودين أو حجوزات. |
| `/اكتشف` | قائم في الكود | تصور بنية الدليل: فن وحرفة، طعام وذاكرة، طريق وإقامة، ومؤسسات ومبادرات. لا توجد نتائج أو مزودون منشورون. |
| `/للشركاء` | قائم في الكود | يشرح الموافقة، المراجعة البشرية، استقلال الهوية، وحدود النشر. |
| `/انضم` | قائم في الكود | دعوة اهتمام ومسار بناء ملف مزود ومعاينة مراجعة محلية. |
| API منفصل | قائم ومقفَل افتراضيًا | استقبال اهتمام، قائمة مراجعة خاصة، وقرار مسبب؛ لا نشر عام. |

الصفحات العامة **تصور منتج قابل للعرض** وليست دليلًا حيًا. لا تعرض أسماء مزودين أو أسعارًا أو حجوزات أو تقييمات أو ميزات وصول غير متحققة، التزامًا بحدود المنتج.[3]

## 3. كيف يشغّل كل تطبيق؟

### 3.1 Urban‑Sense

| المجال | الموجود | شرط التشغيل |
|---|---|---|
| الواجهة والخادم | React 19 + Express + tRPC + Drizzle + MySQL/TiDB | `pnpm install --frozen-lockfile` ثم `pnpm dev` داخل `apps/web`. |
| الجودة | فحص أنواع واختبارات وبناء | `pnpm check` ثم `pnpm test` ثم `pnpm build`. |
| قاعدة البيانات | مخطط وترحيلات خاصة بالبلاغات | `DATABASE_URL` مخصص للبيئة؛ لا يلتزم في GitHub. |
| الهوية | Manus OAuth في بيئة Manus | مفاتيح وجلسات البيئة المدارة فقط؛ لا ينسخ الاتصال إلى التطبيقات الأخرى. |
| الأدلة | تخزين كائنات S3 مع تفويض رفع | يظل مرجع الملف في قاعدة البيانات والبايتات في التخزين، لا في أعمدة قاعدة البيانات. |
| النشر | مشروع Manus قائم | حفظ نقطة إصدار في مشروع Urban‑Sense الحي بعد تحقق الواجهة والمسار؛ لا يعاد نشره من SENSE Experience. |

### 3.2 SENSE Experience

| المجال | الموجود | ما يلزم قبل الإنتاج |
|---|---|---|
| واجهة الويب | React + Vite، عربية RTL، صفحات عامة ومسار مزود | `pnpm dev` داخل `apps/sense-experience` للمعاينة. |
| الخدمة | Express + tRPC مستقلة | `pnpm dev:api` أو `pnpm start:api` بعد إعداد البيئة الخاصة. |
| الجودة | فحص أنواع واختبارات وبناء | `pnpm check` ثم `pnpm test` ثم `pnpm build`. |
| قاعدة البيانات | مخطط Drizzle وترحيلات `sx_*` | قاعدة MySQL منفصلة تمامًا وتطبيق الترحيلات عليها بعد المراجعة. |
| قبول بيانات حقيقية | غير مفعّل | `SENSE_EXPERIENCE_DATABASE_URL` مستقل، وتفعيل صريح بعد اكتمال بوابة المراجعة. |
| هوية المراجعين | جداول وعقد هوية موجودة | مزود OAuth/OIDC مستقل، تحقق جلسة خادم، سجل هوية مفعّل ودور `reviewer` أو `administrator`. |
| النشر | لا رابط إنتاج حاليًا | مشروع نشر مستقل، نطاق مستقل، TLS، سياسة خصوصية/حذف، ومراجعة قبول قبل فتح نموذج البيانات الحقيقية. |

> **قاعدة حاسمة:** لا يُستخدم `DATABASE_URL` الخاص بـUrban‑Sense، ولا OAuth الخاص به، ولا أي مستخدم أو سر أو جدول تابع له لتشغيل SENSE Experience.[4]

## 4. قاعدة البيانات والبيانات: من يملك ماذا؟

| مجال البيانات | المالك | أمثلة سجلات | من يحق له الوصول | ما لا يجوز مشاركته |
|---|---|---|---|---|
| البلاغات المدنية | Urban‑Sense | بلاغ، حالة، إسناد، دليل، قرار مشرف، سجل تدقيق | المواطن صاحب البلاغ وموظفو البلدية ضمن النطاق | لا ينتقل إلى السياحة أو المتجر أو SENSE العام. |
| اهتمام المزود السياحي | SENSE Experience | `sx_provider_interest` | صاحب الطلب والمراجع المخول | قناة الاتصال والوصف الخاص لا يصبحان ملفًا عامًا تلقائيًا. |
| قرار مراجعة مزود | SENSE Experience | `sx_interest_review_decision`, `sx_audit_event` | مراجع مخول ومدير | لا يمرر إلى أي تطبيق تجاري أو بلدي. |
| ملف مزود عام | SENSE Experience لاحقًا | معرف عام، اسم العلامة، وصف موافق عليه، حالة تحقق | الزائر العام | لا يبدأ هذا الجدول أو النشر قبل الموافقة والمراجعة. |
| الكتالوج والطلب والدفع | Commerce لاحقًا | عنصر منشور، مخزون، طلب، استرداد، دفع | عميل/بائع/تشغيل تجارة مصرح | لا ينسخ بيانات الاتصال الخاصة أو ملاحظات المراجعة من السياحة. |
| المال والمحاسبة | دفتر مالي مستقل أو مزود محاسبي مستقل | فاتورة، قبض، مصروف، عهدة، تسوية | الإدارة المالية المخولة | لا يحفظ في جداول بلاغات أو ملفات مزودين أو متصفح محلي. |

### نموذج الحد الأدنى للبيانات المستقبلية

لا يحتاج المشروع «قاعدة بيانات واحدة كبيرة». يحتاج قواعد صغيرة ومحددة الغرض مع معرفات عامة وعقود نشر ضيقة. أي نقل بين التطبيقات يمر عبر حدث أو واجهة موثقة، مثل: `approved_provider_public_summary` أو `published_catalog_item`، لا عبر قراءة جدول داخلي لتطبيق آخر.[1]

## 5. نظام المحاسبة المقترح

**الحالة الحالية:** لا يوجد نظام محاسبة أو بوابة دفع أو دفتر إيرادات تشغيلي داخل المستودع. هذا مقصود؛ لا ينبغي بناء محاسبة داخل واجهة سياحية أو بلدية قبل وجود الكيان القانوني والسياسة المالية والمحاسب المسؤول.

### 5.1 التصميم الذي أوصي به

يُبدأ بأداة محاسبة مستقلة أو مزود محاسبي مرخص، وليس بجدول Excel مشترك أو جداول داخل Urban‑Sense. يبقى المستودع مصدرًا لعقود التكامل وواجهات التقارير، بينما تبقى قيود الدفتر ووثائق الفواتير داخل النظام المالي المخصص. عند الحاجة إلى ربط تشغيلي، يقرأ التطبيق **ملخصات مرجعية فقط** مثل `invoice_status` أو `payment_reference`، ولا يتعامل مع أرقام بطاقات أو بيانات حسابات بنكية.

| الطبقة | القرار المقترح | الضابط |
|---|---|---|
| الكيان المالي | يبدأ باسم الكيان المسجل عند اعتماده | لا تصدر فاتورة باسم «فريق» غير مسجل من دون مراجعة محاسب محلي. |
| دليل الحسابات | إيرادات حسب خط الخدمة، تكلفة مباشرة، مصروف تشغيلي، أصول معدات، ذمم، ضرائب/التزامات | يوحد التعريفات من أول يوم ولا يخلط المشروع/العميل/الشريك. |
| الإيرادات | مشروع، اشتراك، تدريب، تصنيع، عمولة أو بيع مستقبلي | يسجل كل مصدر إيراد مع رقم عقد/فاتورة ومرحلة قبض واضحة. |
| المصاريف | معدات، مواد خام، إنتاج، استضافة، تسويق، أجور/دفعات شبكة العمل الحر، تنقل | مرفق مصدر لكل قيد وموافقة منفصلة عن طالب المصروف. |
| الأصول | طابعة ثلاثية الأبعاد، ليزر، CNC أو تجهيزات مستقبلية | سجل أصل، فاتورة، مالك، موقع، عمر إهلاك يحدده المحاسب. |
| الموافقات | مُنشئ طلب ≠ معتمد ≠ منفذ دفع ≠ مراجع تسوية، بقدر ما يسمح حجم الفريق | موافقة ثانية للمبالغ فوق حد يقرره الفريق كتابة. |
| الإغلاق الشهري | مطابقة بنك/صندوق، ذمم، فواتير معلقة، أصول، إيرادات مؤجلة، ومراجعة ميزانية | تقرير شهري موقع داخليًا قبل مشاركة أي أرقام خارجية. |

### 5.2 لوحات مالية لا تبدأ قبل وجود مصادر أصلية

لا نضع أرقام إيراد أو أرباح أو وظائف في الموقع العام ما لم تأتِ من دفتر مالي أو عقد أو سجل موارد بشرية موثق. داخليًا، تبدأ لوحة الإدارة بأربعة مؤشرات: **السيولة النقدية الفعلية، المبالغ المستحقة للقبض، التزامات الثلاثين يومًا، وهامش كل خط خدمة بعد التكاليف المباشرة**. هذه مؤشرات تشغيلية مقترحة وليست توقعات مالية أو ضمانًا للأداء.

## 6. الأهداف ومؤشرات الأداء والأثر

### 6.1 قاعدة القياس

كل مقياس يتضمن تعريفًا، مالكًا، مصدر بيانات، دورية، خط أساس، هدفًا، وملاحظة عن القيود. نفرق بين:

1. **نشاط/مخرج:** ما نفذناه أو قدمناه؛ مثل عدد ملفات الاهتمام.
2. **نتيجة:** ما تغير لدى المستفيد أو الخدمة؛ مثل انخفاض زمن الإسناد أو اكتمال ملف مزود.
3. **أثر:** تغير أوسع لا ينسب للتطبيق تلقائيًا؛ مثل تحسن دخل الخريجين. لا يدّعى إلا بدليل وخط أساس ومقارنة أو متابعة مناسبة.

هذا الفصل بين القياس الكمي والنوعي وبين النتائج الإيجابية والسلبية يتسق مع فكرة استخدام مؤشرات أثر معيارية لإدارة الأداء لا للتسويق فقط.[5] ويستلزم إدماج الإتاحة وحماية الحقوق وعدم ترك الفئات الأقل اتصالًا خارج الخدمة.[6] [7]

### 6.2 لوحة Urban‑Sense

| طبقة القياس | المؤشر | المصدر | التواتر | ملاحظة تحقق |
|---|---|---|---|---|
| تشغيل | عدد البلاغات المكتملة الحقول | قاعدة البلاغات | أسبوعي | لا يعد البلاغ المكرر أو المسودة بلاغًا مكتملًا. |
| سرعة خدمة | زمن الإقرار وزمن الإسناد | طوابع حالة التقرير | أسبوعي/شهري | يقاس بالوسيط وبالنسبة المئوية، لا بالمتوسط فقط. |
| جودة إغلاق | نسبة الإغلاقات المدعمة بدليل ومراجعة مشرف | أدلة + قرار إغلاق | شهري | لا تقاس «الإغلاقات» من دون دليل مقبول. |
| متانة الحل | معدل إعادة فتح البلاغ | انتقالات الحالة | شهري | يوضح ما إذا كان الإغلاق مستدامًا. |
| تجربة المواطن | تقييم المواطن الحقيقي بعد الإغلاق | جدول التقييم | شهري عند توافر العينة | لا تنشأ تقييمات لتعبئة اللوحة. |
| إتاحة وإنصاف | إكمال المسار حسب القناة/اللغة/احتياجات الإتاحة المصرح بها | تحليلات موافق عليها | ربع سنوي | تجمع بأقل بيانات ممكنة ولا تفسر كأثر سببي وحدها. |

هذه المؤشرات تعتمد أساسًا على بوابة التجربة المغلقة الموثقة: زمن الإقرار والإسناد، إغلاق مدعوم بدليل، إعادة الفتح، وتقييم المواطن.[2]

### 6.3 لوحة SENSE Experience

| طبقة القياس | المؤشر | يبدأ متى؟ | المصدر | الشرط |
|---|---|---|---|---|
| سلامة القبول | عدد طلبات الاهتمام المكتملة | بعد فتح الاستقبال الحقيقي فقط | `sx_provider_interest` | موافقة واضحة وسياسة احتفاظ. |
| جودة المراجعة | زمن القرار ونسبة القرارات ذات السبب الكافي | بعد OAuth/الأدوار | `sx_interest_review_decision` | لا قرار من متصفح محلي أو هوية غير موثقة. |
| تحول المسار | نسبة المدعوين الذين يكملون ملفًا موثقًا | بعد بناء ملف المزود العام | مسار الملف | لا تعد «دعوة» نشرًا أو اعتمادًا. |
| جودة الدليل | نسبة الملفات ذات موافقة نشر متجددة وحقول وصول موثقة | بعد وجود ملفات حقيقية | ملف مزود عام | لا توصف ميزة وصول قبل تحقق المصدر. |
| نتيجة اقتصادية | استفسارات، حجوزات أو مبيعات منسوبة | بعد تكامل حقيقي وموافقة مزود | تكامل حجز/تجارة | لا تجمع قبل وجود تعريف إسناد واضح. |
| تجربة المزود | رضا المزود عن وضوح الانضمام والمراجعة | بعد عينة حقيقية | استبيان اختياري | يعرض حجم العينة ومعدل الاستجابة. |

### 6.4 مسار أرض كنعان ومركز التصنيع الرقمي المقترح

لا توجد حتى الآن قاعدة تشغيلية مشتركة أو مركز مكتمل يجب قياس أثره. عند تفعيل شراكة موثقة، يبدأ القياس بخط أساس بسيط: عدد المتدربين/الخريجين المشاركين بموافقة، عدد الأعمال أو النماذج التي تم توثيقها، وعدد المسارات التي انتقلت من تدريب إلى ملف أعمال أو عرض سوق. لا يُستخدم عدد «الوظائف المتوقعة» أو «زيادة الدخل المتوقعة» بوصفه نتيجة متحققة.

## 8. خارطة الإطلاق: ما الخطوة التالية تحديدًا؟

| الترتيب | القرار أو العمل | مخرج القبول | لا ننتقل قبل |
|---|---|---|---|
| 0 | تثبيت حوكمة Sense: المالك، الأدوار، صلاحيات القرار، الشراكات، والشكل القانوني المقترح | مذكرة مؤسسين/شراكة ومصفوفة صلاحيات يراجعها مختص محلي | تحديد من يوقع العقود ومن يوافق على الصرف والبيانات. |
| 1 | إكمال البلاطات التحريرية لصفحات Urban‑Sense العامة | صفحات محسنة، اختبار RTL ومحمول، لا تغيير في دورة البلاغ | الحفاظ على وضوح التطبيق البلدي ونطاقه. |
| 2 | نشر SENSE Experience كتطبيق مستقل | نطاق وبيئة منفصلان، TLS، بناء ناجح، سياسة خصوصية، صفحة حالة صادقة | لا تقبل بيانات مزودين حقيقية. |
| 3 | فتح بوابة بيانات SENSE Experience | قاعدة مستقلة، ترحيلات، OAuth/OIDC مستقل، أدوار مراجعين، سجل احتفاظ، اختبار قبول | لا دليل عام أو حجوزات. |
| 4 | تجربة مزودين محدودة مع جهات وافقت صراحة | مجموعة صغيرة بمالكي ملف محددين وقرارات مراجعة | لا أسماء أو تقييمات أو أسعار مفبركة. |
| 5 | بناء الموقع العام | روابط صادقة لكل منتج، صفحة شراكات، سياسة إتاحة، وقائمة حالة المنتجات | لا حساب موحد أو بيانات تشغيل داخله. |
| 6 | نواة تجارة مستقلة | كتالوج مراجَع، مخزون، طلبات، سياسة إرجاع، دفتر محاسبة، وشريك دفع معتمد | لا مدفوعات أو شحن حي قبل العقد والاختبار. |
| 7 | طبقة قياس أثر | سجل مقياس، خط أساس، مالك، لوحة تشغيل، مراجعة ربع سنوية | لا ادعاء أثر أو دخل أو وظائف من دون بيانات موثقة. |

## 9. القرارات التي تحتاجك الآن

1. **نطاق أول إطلاق مستقل لـSENSE Experience:** هل هو صفحة تعريف + دعوة مزودين فقط، أم بوابة بيانات حقيقية لمجموعة صغيرة؟ التوصية: صفحة تعريف + دعوة فقط حتى تكتمل هوية المراجعين.
2. **الكيان القانوني واسم التعاقد:** من هو الطرف الذي يوقع العقود ويفتح الحساب المالي ويملك العلامة؟ لا تفتح تجارة أو تحصيلًا قبل هذا القرار.
3. **الشراكات:** هل MABA وأرض كنعان شركاء استراتيجيون بعقود منفصلة أم مزودو مساحة/خدمة؟ يحدد ذلك حقوق العلامة، البيانات، الإيراد، والملكية الفكرية.
4. **الميزانية المالية:** هل تستخدمون مزود محاسبة خارجيًا أولًا أم تبنون واجهة متابعة داخلية لاحقًا؟ التوصية: دفتر خارجي موثق أولًا، وواجهة قراءة داخلية لاحقًا.
5. **موافقة الأثر:** ما النتائج التي تقبلون قياسها ببيانات شخصية أو استبيان؟ لا تجمعوا حقول دخل أو إعاقة أو موقع دقيق لمجرد أن القياس يبدو مفيدًا.
