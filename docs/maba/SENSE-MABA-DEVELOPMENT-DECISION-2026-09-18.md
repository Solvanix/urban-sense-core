# قرار التطوير — تكامل مواصفة MABA مع SENSE

**التاريخ:** 18 سبتمبر 2026  
**المستودع:** `Solvanix/urban-sense-core`  
**مرجع المواصفة:** `MABA-SPEC-TNC-2026-01`، الإصدار 1.0، 13 سبتمبر 2026

## 1. خلاصة القرار

لن نبدأ ببناء نظام NFC كامل ذي محفظة ونقل وتحكم دخول داخل المستودع دفعة واحدة. القرار هو تطوير **طبقة تكامل وإثبات مفهوم تدريجي** تحت مسار مستقل، مع الحفاظ على SENSE بوصفها منصة سياحية ومتجرًا وطنيًا.

الأولوية الأولى هي بناء «جسر MABA» قابل للعرض والاختبار يربط نموذج SENSE السياحي بالكيانات التشغيلية في المواصفة: السائح، البطاقة، الوجهة، العرض، التاجر، الرحلة، نقطة الوصول، والبلدية. في هذه المرحلة لا يوجد رصيد مالي حقيقي، ولا خصم مالي حقيقي، ولا قراءة NFC ميدانية، ولا تكامل دفع أو نقل إنتاجي.

## 2. ما وجدناه في المستودع

المستودع العام يعمل كمستودع متعدد المشاريع وليس كنظام واحد مكتمل. يحتوي على تطبيقات وتجارب متعددة، منها تطبيقات SENSE السياحية والقصصية، تطبيق ويب بخلفية واختبارات، واجهات تصور منشورة، وملفات WordPress ومحتوى تحريري. توجد بالفعل إشارات إلى البلديات والتقارير والتحقق وملفات `maba-bridge`، كما توجد اختبارات لخوادم الويب ومسارات الصلاحيات.

هذا مفيد كقاعدة منتج وتجربة، لكنه لا يساوي تنفيذ مواصفة MABA. المكوّنات التي تتطلبها المواصفة — مثل .NET 8، PostgreSQL 16، Flutter للسائح والتاجر، OpenID Connect، Redis/RabbitMQ، SQLite على الأجهزة، MQTT، إدارة مفاتيح NTAG424، DESFire، محفظة مركزية، وتسوية مالية — ليست مثبتة بوصفها نظامًا تشغيليًا متكاملًا داخل المستودع الذي جرى تدقيقه.

## 3. التحديات الحالية

### 3.1 فجوة النطاق

المستودع يركز حاليًا على المحتوى السياحي، تجربة الزائر، التحقق، النماذج البلدية والتصورات. المواصفة تضيف منتجًا ميدانيًا حساسًا يتعامل مع المال والهوية والنقل والتحكم بالدخول. الخلط بين المسارين سيؤدي إلى ادعاءات غير صحيحة وبنية يصعب اختبارها.

### 3.2 غياب حد فاصل واضح بين النموذج والإنتاج

توجد بيانات وتصورات موسومة بأنها أولية أو تجريبية، وهذا جيد، لكن يجب أن يكون هذا الوسم حاضرًا أيضًا في كل واجهة تدّعي بطاقة أو محفظة أو عرضًا أو رحلة. أي شاشة NFC حالية يجب أن تكون «تصورًا» أو «محاكاة» إلى أن تدعمها خدمة حقيقية واختبارات قبول.

### 3.3 عدم وجود عقد بيانات موحد لـ MABA

نحتاج إلى عقد موحد للكيانات الأساسية، مع حالات المصدر والثقة والملكية والتاريخ: `TouristProfile`, `Card`, `Merchant`, `Offer`, `Trip`, `Fare`, `AccessPoint`, `Municipality`. يجب أن يميز العقد بين المحتوى السياحي وبين المعاملة المالية أو الأمنية.

### 3.4 الأمن والامتثال غير محسومين

المواصفة تفترض إدارة مفاتيح، مصادقة بطاقات، سجل تدقيق غير قابل للتعديل، تقليل البيانات الشخصية، وسياسات احتفاظ. لا ينبغي كتابة مفاتيح أو أسرار أو بيانات بطاقات حقيقية في GitHub العام. كما يجب اعتماد نموذج تهديد وسياسة خصوصية واتفاقيات قانونية قبل أي تجربة ميدانية.

### 3.5 الاعتماد على أجهزة لم تُختبر

المواصفة نفسها تشترط بوابة تحقق للعينة قبل شراء الكمية. لذلك لا يجوز اختيار قارئ أو طابعة أو جهاز مركبة من الاسم التجاري فقط. المطلوب إثبات دعم SUN/CMAC وSDK والاتصال والطاقة والبيئة والأداء، ثم حفظ تقرير العينة.

### 3.6 جاهزية WordPress محدودة لهذا النطاق

WordPress مناسب للمحتوى والقصص والوجهات وصفحات المتجر التعريفية، لكنه ليس المكان المناسب لتخزين الرصيد أو تشغيل محرك التعرفة أو استقبال أحداث NFC. سيبقى WordPress طبقة نشر محتوى، بينما تكون العمليات الحساسة في API مستقل، مع نشر مسودات أو بيانات قراءة فقط عند الحاجة.

### 3.7 تحدي قابلية الصيانة

تعدد التطبيقات والفروع والمجلدات يرفع خطر تكرار المنطق واختلاف تعريف «الوجهة» أو «الشريك» بين تطبيق وآخر. نحتاج إلى مسار منتج معلن ووثيقة ملكية للمكونات قبل إضافة تطبيق جديد.

## 4. ما سنطوره الآن

### المسار A — تثبيت عقد المجال والحدود

- إنشاء `docs/maba/DOMAIN-CONTRACT-v1.md` يعرّف الكيانات والحقول والحالات.
- إضافة حالات واضحة: `prototype`, `verified`, `pilot`, `production`.
- فصل «المعلومة السياحية» عن «المعاملة» وعن «بيانات البطاقة».
- اعتماد سجل مصدر وتاريخ تحديث ومالك لكل بيانات الوجهة أو العرض.

### المسار B — جسر قراءة فقط بين SENSE وMABA

- توحيد صفحة `maba-bridge` لتعرض كيف تتحول الوجهة إلى موقع/نقطة وصول، وكيف يتحول الشريك إلى تاجر، وكيف يرتبط العرض بالرحلة.
- إضافة مخطط تدفق دورة السائح من الاكتشاف إلى التجربة والمنتج.
- عدم إضافة رصيد مالي أو خصم حقيقي في هذه المرحلة.
- استخدام بيانات تجريبية صريحة غير قابلة للاستخدام التجاري.

### المسار C — إثبات مفهوم NFC محدود وآمن

بعد اعتماد العقد فقط، ينفذ نموذج منفصل يثبت: قراءة معرّف تجريبي، التحقق من رسالة موقعة أو QR بديل، حالة البطاقة، تسجيل حدث تدقيقي، والعمل المحلي المؤجل. لا يختبر النموذج أموالًا حقيقية أو دخولًا حقيقيًا أو أجهزة بوابات قبل توفر عينة معتمدة.

### المسار D — الاختبارات والتشغيل

- اختبارات عقد البيانات والتحقق من الصلاحيات والعزل البلدي.
- اختبارات idempotency لمنع تكرار الاسترداد أو المعاملة.
- اختبار طابور عدم الاتصال والمزامنة وإعادة المحاولة.
- اختبار سجل التدقيق وعدم كشف البيانات الشخصية.
- إضافة CI للتحقق من البناء والاختبارات والوثائق قبل الدمج.

### المسار E — التكامل التحريري وWordPress

- إبقاء WordPress قناة للمحتوى السياحي والقصص والتقارير والبطاقات التعريفية.
- نشر حالات «قيد التحقق» و«تجريبي» بوضوح.
- عدم عرض أسعار أو رصيد أو حجز أو خصم حقيقي قبل اعتماد التشغيل.
- توحيد روابط GitHub ومصادر الوسائط وحالات الحقوق.

## 5. ما لن نطوره الآن

- محفظة مالية حقيقية أو بوابة دفع.
- خصومات مالية حقيقية وتسويات بنكية.
- تشغيل حافلات أو أجهزة تحقق ميدانية.
- تحكم فعلي في بوابات المتاحف أو المواقع.
- إصدار بطاقات بكميات أو تخصيص مفاتيح إنتاجية.
- تتبع الأطفال أو الأمتعة BLE.
- تكامل Apple Wallet أو Google Wallet.
- ادعاء سعة 100,000 بطاقة أو مليون معاملة دون اختبار أداء موثق.

## 7. معيار الانتقال من النموذج إلى Pilot

لا ننتقل إلى Pilot إلا بعد توفر: مالك قرار واحد، بلدية أو شريك محدد، سياسة بيانات وخصوصية، عقد مجال معتمد، بيانات اختبار غير حساسة، سيناريو فقدان بطاقة، آلية إبطال، سجل تدقيق، اختبار عدم اتصال، تقرير عينة جهاز، وموافقة مكتوبة على النطاق.

## 8. قرار العلاقة مع WordPress

WordPress يظل الواجهة التحريرية للمنصة السياحية والمتجر الوطني. سيُعرض تكامل MABA في صفحات شرح وقصص وتجارب وبطاقات قراءة فقط. API التشغيل — إن تم بناؤه — يعيش مستقلًا، ولا تُحفظ الأسرار أو الأرصدة أو سجلات البطاقات في WordPress أو المستودع العام.

## 9. النتيجة

المستودع لا يحتاج الآن إلى «إضافة NFC» سطحية، بل يحتاج إلى **حدود منتج وعقد تشغيل واختبار إثبات مفهوم**. هذا هو التطوير الذي يحافظ على هدف SENSE ويستفيد من مواصفة MABA دون تحويل المستودع العام إلى نظام مالي أو أمني غير جاهز.
