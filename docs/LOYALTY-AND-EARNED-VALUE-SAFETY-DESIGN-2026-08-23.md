# نموذج SENSE للاستحقاق والولاء: نقاط، قسائم، وقيمة مالية

**الحالة:** تصميم مقيد للمراجعة؛ لا توجد محفظة، ولا رصيد، ولا نقاط حقيقية، ولا رقم هاتف محفوظ أو موصول حتى الآن.  
**الغرض:** تمكين المروج أو مزود المنتج أو مزود الخدمة من فهم ما قد يستحقه مقابل نشاط موثق، من دون أن تتحول SENSE إلى جهة تحويل أموال أو مشغل محفظة بلا ترخيص أو عقد.

## 1. الفصل الذي لا يجوز تجاوزه

| طبقة القيمة | تعريفها داخل SENSE | ما يجوز في النموذج الأول | ما يبقى مغلقًا |
|---|---|---|---|
| **نقاط SENSE** | وحدات تقدير غير نقدية لسجل نشاط موثق | إظهار الأهلية، منح نقاط بعد مراجعة، وقواعد انتهاء أو إلغاء معلنة | لا تحويل إلى نقد، لا بيع، لا تحويل بين الأشخاص، ولا قيمة مضمونة بعملة |
| **قسيمة ممولّة من تاجر** | عرض يصدره تاجر معتمد بقيمة وشروط وتاريخ انتهاء | عرض حالة قسيمة مستحقة بعد عقد تاجر وإصدار رمز فريد | لا تمويل من SENSE، لا خصم أو استرداد تلقائي، ولا قسيمة وهمية |
| **قيمة مالية/محفظة** | دفعة أو تحويل أو رصيد في محفظة منظمة | لا شيء قبل شراكة مزود مرخص، KYC عند اللزوم، موافقة، وسجل تسوية | لا إرسال إلى رقم هاتف أو IBAN أو محفظة عبر SENSE الآن |

> الرقم الهاتفي ليس «مفتاحًا للنقاط» في المرحلة الحالية؛ هو معرف حساس يمكن أن يصبح وسيلة تحقق أو وجهة تحويل فقط بعد أن يوافق صاحبه، ويثبت أنه يسيطر عليه، ويعتمد المشغل مسارًا تعاقديًا وتقنيًا.

## 2. ما تحقق من مزودي الخدمة علنًا

| الاسم الذي ذُكر | ما تثبته الصفحة الرسمية | ما لا تثبته علنًا | النتيجة لـSENSE |
|---|---|---|---|
| **Reflect** | برنامج نقاط للمستخدم النهائي داخل تطبيق مصرفي رقمي، ونقاط مرتبطة بأنشطة ومعاملات محددة | لا وثائق عامة لواجهة تاجر تتيح لـSENSE إيداع نقاط Reflect أو ربط رقم عميل بها | مرجع تصميمي لشفافية قواعد النقاط فقط، لا تكامل مقترح حاليًا |
| **PalPay / Mahfazati** | محفظة منظمة، دفع للتاجر عبر QR، وخدمات تجار وشركات معلنة | لم تُنشر في الصفحات التي راجعناها وثائق API عامة لتنفيذ دفعات أو قسائم أو إيداعات SENSE إلى رقم هاتف | مرشح لمحادثة أعمال رسمية لاحقًا، وليس API يمكن افتراضه أو استخدامه الآن |
| **iBURAQ** | تحويل محلي فوري عبر Bank-e إلى بنك/محفظة، ويمكن أن يستعمل رقمًا مسجلًا ضمن الخدمة | لا وثائق عامة لتكامل SENSE كتاجر أو كمرسل دفعات جماعية، ولا ينبغي اعتبار رقم الهاتف كافيًا للتحويل | مسار دفع منظم محتمل فقط بعد عقد وموافقة مزود وهوية المستفيد؛ لا يدخل النموذج الأول |

## 3. دفتر الاستحقاق المقترح

كل استحقاق لاحق يحتاج سجل أحداث غير قابل للتعديل يتضمن: معرف حامل الاستحقاق الداخلي، الدور، سبب الاستحقاق، مرجع الدليل أو قرار المراجع، نوع القيمة، الحالة، وتاريخ الانتهاء. لا يكتب هذا الدفتر رقم الهاتف في الحدث نفسه. ويحظر أن ينشأ حدث بقيمة سالبة أو تحويل أو نقد من واجهة المستخدم.

| الحالة | من ينشئها | معناها |
|---|---|---|
| `proposed` | قاعدة نشاط موثق أو مراجع | اقتراح استحقاق، ليس رصيدًا |
| `approved` | مراجع مخول أو قاعدة معتمدة | يمكن عرضه كنقاط أو أهلية لقسيمة |
| `redeemable` | مشغل القسيمة بعد عقد تاجر | يصبح رمزًا أو عرضًا محدد الشروط |
| `redeemed` | نقطة استرداد التاجر أو مزود معتمد | سجل إثبات الاسترداد فقط |
| `reversed` | مراجع مع سبب تدقيقي | تصحيح بسبب خطأ أو دليل غير صالح |

## 4. ربط رقم الهاتف: بوابة لا حقل إدخال حر

لا يطلب النموذج العام رقم هاتف. عند اعتماد شريك، تفتح رحلة مستقلة بهذه الترتيب: إفصاح غرض الربط → موافقة صريحة منفصلة → إدخال رقم بصيغة موحدة → رمز تحقق لمرة واحدة من مزود معتمد → تخزين مرجع مزود أو بصمة مجزأة للرقم، لا الرقم المقروء في سجل النقاط → خيار فصل الربط → سجل تدقيق. أي تغيير وجهة مالية يحتاج تحققًا جديدًا وتأكيدًا من المستخدم.

## 5. بوابات ما قبل التشغيل

1. اختيار مشغل البرنامج: من يدفع القسائم أو يمول النقاط؟
2. شروط أهلية مكتوبة تمنع التمييز أو التلاعب أو الادعاءات الزائفة.
3. سياسة خصوصية وحذف وربط هاتف وفض نزاع.
4. عقد وواجهة API أو لوحة تاجر رسمية مع PalPay أو أي بديل؛ لا يعتمد على افتراض وجود API.
5. مراجعة امتثال مالية وقانونية محلية قبل أي قيمة قابلة للتحويل أو السحب.
6. دفتر أحداث وتدقيق وتسوية، واختبار بيئة تجريبية قبل أول دفعة.
